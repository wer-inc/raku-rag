# 0022 — 同期→根拠文書レビュー→AIドラフトレビューの全体フローが直感的に見えない(系統 = approval / workflow / ia)

> Priority: **P2 / Medium** / Status: In Progress / Labels: `approval`, `workflow`, `information-architecture`, `ux`, `onboarding`

## 背景(なぜ今)

ユーザー確認で、データソース同期、`review_required` / `trusted`、根拠文書レビュー、AIドラフトレビューの
個々の意味は説明すれば理解できるが、UI 上では一連の作業フローとして直感的に見えないことが分かった。

直近でナビ文言は `レビューキュー` → `AIドラフトレビュー`、`文書承認` → `根拠文書レビュー`、
`承認ルール` → `同期・承認ポリシー` に改善したが、これは用語の改善に留まる。根本的には、
ユーザーが「いま自分はどの段階にいて、次に何をすべきか」を画面構造から把握しづらい。

## どんな課題か

- `同期・承認ポリシー`、`根拠文書レビュー`、`AIドラフトレビュー` がナビ上で横並びになっており、
  依存関係や順番が見えない。
- `review_required` を選ぶと同期後に文書が `pending_review` で根拠文書レビューに入る、という重要な流れが
  画面遷移として自然に伝わらない。
- `trusted` と `review_required` の選択が、その後のレビュー負荷・高リスク回答可否にどう効くかが
  初見でつながらない。
- 根拠文書レビューと AIドラフトレビューの2段構えはプロダクトとして良いが、UI では「なぜ2つあるのか」が
  ユーザーの頭に入る前に別画面へ分散している。
- ホーム/ソース追加/レビュー各画面に点在する説明文だけでは、作業全体のメンタルモデルを作りにくい。

期待挙動:

- ユーザーが「ソースをつなぐ → 同期する → 根拠文書を正式化する → AI生成物をレビューする」という流れを
  画面構造から自然に理解できる。
- 各画面は単独機能ではなく、前後の状態と次アクションを示す。
- `trusted` と `review_required` の選択結果が、レビューキュー/根拠化/高リスク回答への影響として見える。

実際の挙動:

- 画面名を読んでも、どれが先で、どれが後で、どの状態のデータが入ってくるか分かりにくい。
- 会話で説明すれば理解できるが、UIだけでは直感的ではない。

## どこで起きたか

- 画面: `/sources/new` のソース追加・アップロード/接続設定
- 画面: `/reviews/documents` の根拠文書レビュー
- 画面: `/reviews` の AIドラフトレビュー
- 画面: `/reviews/settings` の同期・承認ポリシー
- 画面: `/home` のタスク/クイックアクセス
- コード: `apps/web/app/components/FullSaasScreen.tsx`
- コード: `apps/web/lib/full-saas.ts`
- 環境: local UI review
- run id / ingestion id / correlation id: なし
- 再現条件:
  1. 初見ユーザーとしてデータソースを追加する。
  2. `review_required` / `trusted` を選ぶ。
  3. 同期後にどの画面へ行き、何を承認し、AIドラフトレビューがいつ必要になるかを UI だけで判断する。

## 影響

- 営業デモへの影響: 説明すれば良いフローなのに、画面だけでは価値が伝わりにくい。
- 本番クライアントへの影響: データソース設定後にレビューすべき対象を見失い、`pending_review` 文書が滞留する。
- データ品質: 根拠文書が承認されないまま残り、高リスク回答で `approved_citation_missing` が増える。
- UX: `根拠文書レビュー` と `AIドラフトレビュー` の違いを都度説明する必要がある。
- 運用: 管理者、レビュア、現場ユーザーの担当範囲が曖昧になりやすい。

## どう解決すべきか

1. **情報設計**
   - レビュー系を単なる横並びナビではなく、作業順に見える構造へ再編する。
   - 例: `ナレッジ準備` または `承認ワークフロー` のハブを作り、次の4段階を状態付きで表示する。
     1. データソース設定
     2. 同期結果
     3. 根拠文書レビュー
     4. AIドラフトレビュー
   - 各段階に件数、状態、次アクションを出す。
2. **ソース追加後の導線**
   - `review_required` で同期した後は、成功メッセージだけでなく `根拠文書レビューへ` の明確なアクションを出す。
   - `trusted` で同期した後は、`承認済み根拠として反映済み` とし、必要なら `質問で確認` / `AIドラフト作成` へ誘導する。
3. **画面ごとの役割整理**
   - `根拠文書レビュー`: 「元文書を正式根拠にする」作業に集中する。
   - `AIドラフトレビュー`: 「AIが作った業務成果物を採用する」作業に集中する。
   - `同期・承認ポリシー`: 編集未実装なら、ハブ/設定画面として過剰に見せず、データソース設定との関係を明確化する。
4. **UI 表現**
   - 長い説明文で補うより、状態バッジ、件数、進行ステップ、次アクションで理解させる。
   - `pending_review`、`approved`、`obsolete` はユーザー向けラベルと補助状態を整理する。
5. **テスト方針**
   - Playwright で「review_required 同期後に根拠文書レビューへの導線が出る」ことを確認する。
   - `trusted` 同期後には文書レビュー待ちとして誤誘導しないことを確認する。
   - ナビ/ホーム/ソース追加の文言が同じ概念名で揺れないことを snapshot または unit で固定する。

## QA checklist

- [ ] 初見ユーザーが作業順を UI から説明できる。
- [ ] `review_required` 同期後、根拠文書レビューへの次アクションが表示される。
- [ ] `trusted` 同期後、個別レビュー不要であることと次アクションが表示される。
- [ ] 根拠文書レビューと AIドラフトレビューの対象が混同されない。
- [ ] ホーム/ナビ/ソース追加/レビュー画面で用語が揺れない。
- [ ] tenant/ACL 境界を越えない。
- [ ] security/safety gate を弱めていない。
- [ ] Playwright または API smoke で確認できる。

## 受け入れ条件(DoD)

- 同期からレビューまでのフローが1つの作業として UI 上で追える。
- `review_required` / `trusted` の選択結果が、後続レビューと正式根拠化にどう影響するか分かる。
- 根拠文書レビューと AIドラフトレビューの違いが、説明なしでも概ね伝わる。
- 既存の承認・安全・監査ルールを弱めていない。
- 回帰テストまたは UI smoke が追加されている。
